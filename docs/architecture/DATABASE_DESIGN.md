# Database design

## Engines
The same SQL runs on SQLite (development and tests) and PostgreSQL 16 (Neon in production). It is written in a portable subset of the SQLite dialect, and `app/db.py` translates it for PostgreSQL:
- `?` placeholders become `%s`.
- `CURRENT_TIMESTAMP` becomes UTC text in the same `YYYY-MM-DD HH:MM:SS` format.
- `INTEGER` becomes `BIGINT` and `REAL` becomes `DOUBLE PRECISION`.
- An `id INTEGER PRIMARY KEY` becomes a generated identity, and inserts into such tables return the new id.

The backend suite runs on both engines, because SQLite accepts some SQL that PostgreSQL rejects.

## Conventions
- **Ids:** integer, generated by the database, never reused. `outbox_events.event_id` is also a UUID, so events can be traced across systems.
- **Tenancy:** every tenant-owned table has `org_id`. Queries filter by it. Child tables repeat it where queries need it without a join (`scenes`, `opportunities`).
- **Time:** text in UTC (`CURRENT_TIMESTAMP`). Leases and retry times are Unix seconds (`REAL`).
- **Structured data:** JSON in `TEXT` columns, only for data validated before it is written (for example `opportunities.geometry_json`). Domain fields that are queried get their own columns.
- **Enumerations:** `CHECK` constraints list the allowed values.
- **Money (Phase 11):** integer minor units plus an ISO currency code (AD-6).

## Migrations
`init_db()` runs at start-up. `python -m ops.migrate` runs it explicitly before a deployment. It does two things:
1. **Baseline, frozen.** It applies the `CREATE TABLE IF NOT EXISTS` schemas in `app/main.py`, `app/auth.py` and `app/decisions.py`, then the column list `_MIGRATIONS`. Nothing new is added here.
2. **Ordered migrations.** It then applies the list in `app/migrations.py`. Each migration runs once, in id order, and is recorded in `schema_migrations(id, description, checksum, applied_at)`.

Start-up stops with an error when:
- an applied migration's SQL or code has changed (fix forward with a new migration);
- the database has a migration this code does not know (it was migrated by a newer release);
- the ids are not unique and in order.

Migrations are additive and idempotent. They create tables, columns, indexes and backfills, and drop nothing. Backfills are self-contained: they use only the tables and columns that exist at that point, never application code that may change later.

**Locking and transactions:**
- **PostgreSQL:** all of `init_db` is one transaction under an advisory lock, so the API and the runner can start together. A fingerprint of the whole schema skips the work when nothing changed. It matters on serverless, where new instances start often.
- **SQLite:** each migration commits on its own. A second process that started at the same time sees the record and skips the migration.

`ops/dbtransfer` doesn't copy `schema_migrations` and `schema_fingerprint`, because the target database sets them up itself.

## Foreign keys
The baseline tables have none. Every table added from Phase 1 declares its relationships as `REFERENCES ... DEFERRABLE INITIALLY DEFERRED`. They are checked at commit, which lets `ops/dbtransfer` import tables in any order inside one transaction. Video deletion (Phase 3) is soft (`videos.deleted_at`), so no row a foreign key points to is ever removed.

**Seeded reference data:** migrations write the platform brand-safety terms and scoring configuration `v1`. `ops/dbtransfer` replaces them with the dump's copy on import.

## Legacy tables still written
- **`users`** mirrors each person's membership in their default organization. `members.membership_drift()` checks this, and a test asserts it stays empty.
- **`frames`** is the current keyframe view that the decision engine and the older screens read. Each analysis writes a version; the latest completed one also fills `frames`.

## Known limits
- **The legacy analysis still shares images.** `POST /api/videos/{id}/analyze` still names keyframe images by video and timestamp. The staged pipeline (`POST /api/videos/{id}/analyses`) stores frames under `frames/analyses/a{id}/`.
- **Older videos are hashed gradually.** Database maintenance hashes them, two per run.
- **Rate limits stay in the database** (technical debt 12).
